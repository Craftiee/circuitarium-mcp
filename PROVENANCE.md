# Provenance and evidence policy

Circuitarium MCP is an independently authored interoperability tool. Its first
integration family, **CRUMBLE** (**C**ircuit **R**epresentation &
**U**niversal **M**odel **B**ridge for **L**aboratory **E**lectronics),
documents what was observed at the CRUMB save-file boundary and keeps those
observations separate from general electronics knowledge, inference, and
third-party examples.

CRUMBLE and its CRUMB adapter are unofficial. Circuitarium MCP is not
affiliated with, endorsed by, or sponsored by CRUMB or its developer or
publisher. CRUMB and related names and marks belong to their respective owners.

The Logisim-evolution adapter follows the same independence boundary.
Circuitarium MCP is not affiliated with or endorsed by the Logisim-evolution
project. The repository contains no Logisim-evolution source or binary. Users
provide a separately licensed, user-supplied JAR, which Circuitarium invokes as
an independent local process. The upstream official v4.1.0 all-JAR is the
recommended download, but the runtime does not authenticate a configured JAR
as that asset.

## Repository boundary

This repository includes:

- independently authored TypeScript, tests, documentation, and MCP schemas;
- an independently authored, citation-only Logisim 4.1.0 component identity
  catalog and semantic planning profiles;
- small synthetic `.cru` fixtures generated by this project;
- one small, independently authored `.circ` full-adder and matching vector;
- factual, version-pinned interoperability data manually transcribed from
  controlled saves and inspection of a tested installed build; and
- aggregate analyzer results from external validation designs.

It does not intentionally include:

- CRUMB executables, assemblies, engine or IL2CPP metadata files;
- CRUMB scene files, resource files, textures, models, audio, logos, or other
  game assets;
- decompiled or recovered CRUMB source code;
- copies of developer-published circuit designs used as external validation
  inputs; or
- source-code or EEPROM payloads taken from those external designs;
- Logisim-evolution JARs, source code, or documentation copies; or
- third-party `.circ` designs.

Factual names and numeric identifiers needed to interpret a save are kept in
small, independently authored lookup tables. Those facts are version-specific
observations, not redistributed asset files or behavioral implementations of
CRUMB components.

## Logisim-evolution target and evidence

The Logisim adapter is independently authored and pinned separately:

| Attribute | Value |
|---|---|
| Application | Logisim-evolution |
| Version | `4.1.0` |
| Source-catalog revision | `632d66dca880ac089e2c6c2c383ea20d9c707ee2` |
| CI-verified official build | `main/499134ec` |
| Runtime | Java 21 or newer |
| Project surface | UTF-8 XML `.circ` file |
| Vector surface | documented text `.vec`/`.txt` format |
| Compatibility profile | `logisim-evolution/4.1.0` |
| Adapter version | `logisim.evolution/0.1` |
| Neutral IR | `circuitarium.project-ir/0.1` |

Format and command-line facts are based on the project's public source and
official 4.1.0 documentation/release. Circuitarium code does not copy or link
Logisim implementation code. The official all-JAR is downloaded only by the
version-pinned CI verification job, checked against SHA-256
`fe6386a3217a591bcc311a4eda49e1f43a389b499dd3d0f6f40f344fc85f2577`,
used as a separate process, and never included in a Circuitarium artifact.

The standard-library Resource records exact project-facing identifiers from
the official 4.1.0 source at the pinned revision above. Its classifications,
summaries, verification guidance, and neutral profile schema are independently
authored for Circuitarium; source and manual URLs are citations rather than
embedded upstream content. Identity-only entries deliberately assert no ports
or behavior. The Resource includes no Java, copied source comments, manual
prose, icons, or executable models. Upstream source and documentation remain
under GPL-3.0-only; Circuitarium's independently authored code and catalog
remain under Apache-2.0.

Ordinary runtime configuration is a different trust boundary: the configured
JAR only has to self-report Logisim-evolution 4.1.0. That response can be
spoofed and is returned as `authenticity: "self-reported-unverified"`;
Circuitarium does not compare a user's JAR to the CI digest or authenticate its
publisher.

The committed full-adder `.circ` and vector were authored for this repository.
CI verification establishes that the pinned official 4.1.0 asset loads the
project, emits the expected eight-row table, and passes 8/8 vectors. A local
E2E run establishes behavior only for its configured local JAR. Neither result
generalizes to every `.circ` feature or later Logisim version.

Before runtime execution, Circuitarium defaults to denial for external
file/JAR libraries, VHDL, unsafe or path-bearing runtime features, and unknown
or malformed constructs. It stages the exact already-read project/vector byte
snapshots in private fixed-name temporary files and cleans them up after
success or failure. Test-vector mode additionally copies the configured JAR
into that private directory before probing and execution so upstream startup
cannot discover sibling `logisim-defaults` content. Those controls reduce
project-driven risk; they are not an
operating-system sandbox or a security boundary against a malicious JAR, which
runs with the Java process permissions of the MCP server.

## Evidence categories

`crumb_component_catalog` returns the same distinctions through
`data.evidenceVocabulary`, so a model can interpret the legacy v0.2 confidence
strings without relying on this document alone.

### Independently authored code

Project algorithms, schemas, validation rules, security boundaries, test code,
documentation, and MCP tool definitions are authored for this repository.
They may operate on CRUMB files but are not copied from CRUMB program code.

### Synthetic fixture

A synthetic fixture is emitted by
`src/adapters/crumb/fixtures.ts` from independently maintained data. The five
files in `fixtures/crumb/` are generated test artifacts, not developer circuit
examples. Each was opened in the tested build and visually checked for the
documented result.

Some fixture field values originate in controlled-save observations. A
successful reopen shows that one exact file was accepted by one tested build;
it does not establish a complete format specification or behavioral
correctness.

### Controlled-save observation

A controlled-save observation comes from creating or changing a deliberately
small circuit in the tested application, saving it, comparing the resulting
payload, and, where write support is claimed, reopening a generated equivalent.
The machine-readable catalog represents this class as `controlled`.

Controlled observations currently support the root defaults, structural board
payloads, resistor and LED field layouts/defaults, and the generated fixtures.
The hidden breadboard and rail connectivity rules are an inference from
repeated controlled attachments; those rules remain separately labeled and
version-pinned.

`crumb_compare_designs` helps record the difference between a controlled
baseline and candidate while returning only bounded modeled data and artifact
digests. A comparison result is evidence about those two exact files; it does
not automatically promote a schema candidate, establish write support, or
prove which application build authored either file.

### Installed-build inspection

Installed-build observations are factual names, positional relationships, and
field-use hints manually transcribed while inspecting a locally installed copy
of the tested build. The machine-readable catalog represents this class as
`installed-build`; tool-5 IC confidence tags use
`installed-build-extracted` and `installed-build-partial` for contract-v0.2
compatibility.

In those legacy confidence tags, `extracted` means that a factual label or
ordering was manually transcribed from an observation. It does not mean an
asset file is included in this repository.

Installed-build observations currently support:

- the version/build identifiers above;
- the 21-entry tool-5 prefab label and ordered-pin registry in
  `src/adapters/crumb/icCatalog.ts`; and
- the saved settings and terminal-order notes for tools `7` through `14` in
  `src/adapters/crumb/catalog.ts`.

These observations recognize package structure only. They do not reproduce
game code, simulate CRUMB behavior, or establish electrical correctness.

Developer-published `.cru` designs were used as external compatibility inputs.
The repository retains only bounded aggregate results such as component counts,
recognized schema counts, inferred-group counts, and the fact that sensitive
embedded fields were redacted.

The original external files are not committed or redistributed here. The
contract-v0.2 confidence value `official-example` means evidence observed in a
developer-published example; it does not claim endorsement of this project or
grant redistribution rights.

### Public electronics knowledge

Ordinary facts such as SI units, common component roles, and publicly
documented package terminology may help name or validate the neutral
electronics model. Such knowledge does not, by itself, establish CRUMB's tool
IDs, positional save layout, terminal order, or runtime behavior.

When a future behavioral model relies on a datasheet or another external
technical source, its implementation and documentation should cite that source
separately from CRUMB format evidence.

### Inference and unknowns

`inferred` marks a conclusion that fits observations but is not directly
serialized or fully controlled. `unknown` and neutral terminal names are used
when the evidence is insufficient. The adapter must not replace either with a
plausible electronics guess.

## Hashes and artifact identity

The tools use SHA-256 digests to identify the exact bytes of a project or
embedded payload. A digest supports reproducibility and cross-model handoff: two
agents can confirm that they analyzed the same bytes without exchanging an
absolute filesystem path.

A hash is not proof of authorship, permission, accuracy, safety, or format
compatibility. It is only an identity check. Repository documentation therefore
uses workspace-relative references, and published evidence records must not
contain a contributor's personal filesystem paths.

For evidence that cannot be redistributed, a contribution may record a digest,
the public source reference, acquisition date, exact tested-build identifiers,
and bounded aggregate results without committing the source artifact. A digest
does not make an otherwise non-redistributable artifact suitable for upload.

## Adding or changing format knowledge

A change that expands a CRUMB compatibility claim should:

1. identify the exact application version, platform/build identifier, engine,
   and adapter contract;
2. assign every new claim one of the evidence categories above;
3. prefer a minimized, independently created save with one changed variable;
4. add a synthetic regression fixture when the observation can be represented
   without third-party content;
5. validate the file structurally and reopen generated output in that exact
   build before claiming write support;
6. keep third-party circuit files and installed-build artifacts out of the
   repository unless their redistribution rights are explicit and documented;
7. record uncertainty and conflicting observations instead of silently
   selecting the most plausible interpretation; and
8. use wording such as “observed in the tested build,” not “proved,” when a
   conclusion is limited to inspected behavior.

Reverse-engineering and interoperability rules differ by jurisdiction and
license terms. Contributors are responsible for ensuring that evidence they
submit may be used and redistributed; this policy is project hygiene, not legal
advice.
